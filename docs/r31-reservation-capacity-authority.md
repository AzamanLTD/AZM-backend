# r31 reservation-capacity authority

## Writer and consumer inventory

- Customer `POST /api/reservations`: `reservationController.createReservation`. It previously read availability and then created outside a transaction. It now uses durable tenant/customer request identity and relies on the PostgreSQL trigger as the final conflict authority; a stale preview returns 409.
- Hotel marketplace create: `hotelMarketplaceController.createHotelReservation` checks the physical `HotelRoom`, room block and nightly rate, then delegates to the same customer controller. The preview is not an authority; room/time claims are decided by PostgreSQL.
- Business Portal reservation APIs use the customer reservation route. Business OS front-desk walk-in is the other direct `Reservation.create` writer (`HotelOpsService.createWalkIn`); its room occupancy transition shares one transaction with creation. Its previously invalid `notes` field/missing required `reservationRef` are fixed here.
- Counter-proposal acceptance (`reservationController.acceptCounterProposal`) and Business OS `respond-reschedule` update active date fields; room moves update active `serviceItemId`. All such writes enter the same trigger, including direct Prisma callers. Proposal-only writes do not change held capacity. Confirmation, funding confirmation and check-in retain an existing active claim; cancellation, checkout, no-show and expiry leave it. Resurrecting a terminal row rechecks availability.
- HotelRoomBlock insert/update and a change to indefinite MAINTENANCE status take the same business-level transactional advisory lock and reject conflicting active bookings. DIRTY/CLEANING/OCCUPIED are transient room states, not permanent cancellations of future bookings. HotelRoom status itself is not an availability interval.
- `bookingEscrowService.createBookingEscrow` creates ticket, draft escrow and an eligible reservation link in one transaction. It cannot link a terminal reservation or create a second link. `fundBookingEscrow` and reservation terminal lifecycle claims serialize on the escrow row, with funding, balance, ledger and history in one transaction (r25/r29/r30). The capacity trigger does not move money or create tickets. A losing capacity insert has no linked escrow or ticket.
- `marketplaceController` updates no-show penalty terms, not capacity. `transitOpsService.boardPassenger` updates a transit reservation status to BOARDED, releasing the active claim. Penalty policy settlement enters a terminal state transactionally. Business OS counter-proposal endpoints change only proposal fields until accepted.

## Resource and mechanism

The legacy availability rule is tenant + overlapping `[startDatetime,endDatetime)` + matching location/service item. A null location or service item means a tenant-wide wildcard for that dimension. Two distinct non-null room IDs are independent. The same physical HotelRoom is never made independent by a forged location; a supplied location must match the room's own location. Different businesses never contend for the same logical resource. `allowOverbooking` is an existing business setting, but the old create endpoint did not honor it. This authority intentionally preserves the endpoint's fail-closed single-capacity behavior. Capacity greater than one for service products is not modeled by Reservation and must not be inferred from partySize.

A PostgreSQL BEFORE trigger takes `pg_advisory_xact_lock(hashtextextended(businessProfileId, 91731))`, tests committed overlapping active rows, and aborts the losing write with SQLSTATE 23505. It covers inserts, reactivations, changed resources and changed intervals from **every** writer in every process. Terminal status transitions free the claim when committed, not when a prior read predicts they will. Blocks and indefinite maintenance use the same serialization boundary. Trigger replacement and a historical-overlap preflight take place in one locked DDL transaction; an existing conflict aborts installation, requiring explicit remediation. This is a database-level serialized interval claim, not an application mutex or a read-then-write assertion.

A GiST exclusion constraint on a `(business, resource, tsrange)` key would be attractive for a strict one-resource model, but a nullable location/service item currently means a wildcard that intersects multiple keys. A single equality-based exclusion index would be incorrect. An explicit normalized resource-slot table or range redesign should accompany any later shift to multi-capacity or opt-in overbooking. Existing `timestamp` columns represent half-open intervals without changing stored values.

## Request retries and rollout

`Reservation.clientRequestKey` is unique within `(businessProfileId,customerId)`; `requestFingerprint` covers canonical payload fields. A supplied `Idempotency-Key` (max 128 characters) replays the same row on a byte-equivalent semantic request and returns 409 on materially different payload. Legacy requests without that header use a SHA-256 canonical fingerprint as their fallback identity, so a timeout retry after cancellation cannot silently create a fresh booking. To intentionally rebook the exact cancelled slot, supply a new explicit key. A replay returns the current reservation (including a later terminal status), not a promise that the booking remains active. Other customers and different request keys remain independent, although overlapping availability still rejects them.

Production is `prisma db push` managed. Run `infra/install-reservation-capacity-overlay.js` **after** the Business OS overlay and **before** traffic; both the release chain and two CI lanes install it. It is idempotent and transactional. The production preflight may refuse installation if legacy active reservations already overlap; inspect and reconcile those rows rather than disabling the trigger. This branch does not deploy or merge by itself.

## Known separate issues

- Booking escrow fee/principal arithmetic still passes through JavaScript `Number` and six-decimal rounding in `bookingEscrowService`. This predates r31 and should be a dedicated financial-precision patch. The new reservation amounts and walk-in arithmetic use Prisma Decimal.
- The global `allowOverbooking` flag and a service product's real physical capacity are not modeled as per-resource slot counts. This patch enforces the existing route's single-capacity rule. A later product decision must define capacities and booking policy before relaxing it.
- A room marked currently OCCUPIED/DIRTY/CLEANING remains rejected by the current hotel marketplace precheck even for later dates. This is pre-existing admission behavior, not a consequence of the database collision mechanism; a separate inventory-policy change is needed to sell such future dates safely.
