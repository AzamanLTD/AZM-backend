# r42.1 — Shared Idempotency Closure (audit note)

**Branch:** `r42.1-idempotency-closure` · **Base:** `main` @ `efdff6f`
**Spec:** `#317` review follow-up (r42 tranche 2 — wire every remaining
middleware-protected financial mutation)

## What changed

Every money-moving endpoint that still committed its `FinancialOperation`
claim *after* the response was promoted to the **wired** contract: the claim
commits to `COMMITTED` with the exact wire `responseBody` **inside** the
endpoint's economic `$transaction`. Economics and committed-response identity
commit or roll back together.

### Tranche 2 (this PR — five endpoints)

| Endpoint | Economics | In-tx claim commit |
|---|---|---|
| `POST /api/escrow/fund` | payer lock of principal + fee | `escrowService.fundEscrow` |
| `POST /api/azm-convert` | AZM burn → USDC credit from pool | controller tx |
| `POST /api/azm-gifts/send` | P2P AZM transfer legs | `azmGiftService.sendGiftTransfer` (fresh **and** replay paths) |
| `POST /api/order-book/orders` | balance reserve + match | controller tx |
| `POST /api/p2p/complete` | escrow release settlement | `p2p.service.completeTrade` |

Shared helper: `middleware/idempotency.js → commitOperation(tx, operation, statusCode, body)` —
CAS on `status: 'IN_PROGRESS'`; losing it throws `IDEMPOTENCY_STATE_CONFLICT`
and rolls the whole economic transaction back. Body stored as serialized wire
text (byte-fidelity rule, not JSONB).

All five routes mount `idempotency({ releaseOn4xx: true })`. This declaration
is **valid only because** of the wired commit: a post-response `IN_PROGRESS`
claim is durable proof the transaction rolled back, so the key is safely
releasable. A post-commit failure surfacing as 4xx can no longer delete a
committed claim — the in-tx `COMMITTED` state wins the CAS (proven by §5-H).

Tranche 1 (wired before this PR, on main): transit seat booking, multi-currency
convert, wallet withdrawal, storefront orders, business invoice create.

### Deliberately NOT wired in this PR

* **External-provider sequences** — `POST /api/deposits/initiate` (Moolre),
  wallet deposit/initialize, cross-border susu contribute/payout (local rails).
  Their request/commit boundaries span an outside system; a single-request
  Postgres CAS cannot prove commit, and their in-flight resumability is a
  provider-workflow concern (see "Go boundary candidates" below).
* **State transitions without direct money movement** — escrow
  satisfy/dispute/cancel, p2p ping/accept, susu roster ops. Idempotency
  middleware (retain) is correct there; wiring adds no safety.
* **Savings/vault/peer/internal-transfer** — owned by open PR **#317**
  (first-tranche alias-identity closure). Not touched here to avoid conflict.
  Merging #317 first is recommended; both PRs change disjoint route families.

## Failure/recovery matrix — proven per endpoint

`__tests__/r42.1-idempotency-closure.pg.test.js` (real PostgreSQL, 37 tests):

* **A** first execution: exactly one economic mutation; claim `COMMITTED`;
  stored `responseBody` IS the exact wire bytes served.
* **B** same-key replay: byte-identical wire response; economics never re-run.
* **C** concurrent duplicates: exactly one execution; loser 409 `IDEMPOTENCY_IN_PROGRESS`.
* **D** canonical identity only: no legacy alias path exists on this tranche;
  a legacy-style body field is fingerprinted material payload, never an
  alternative identity (divergent alias value → 409 `IDEMPOTENCY_PAYLOAD_CONFLICT`).
* **E** divergent payload: deterministic 409; committed original untouched.
* **F** missing key: deterministic 400; no claim; no economics.
* **G** pre-economic 4xx: claim released; the SAME key retries successfully
  once corrected (insufficient balance / min-convert / invalid side-amount).
* **H** crash-after-commit: money committed exactly once; claim already
  `COMMITTED`; same-key retry replays the committed result byte-identically;
  economics never re-execute. Strongest case: P2P settlement where the
  post-commit socket failure surfaces as **4xx** — the wired claim survives.
* **I** parked `IN_PROGRESS` claim: same key refuses (409); never executes blindly.

## §7 — Go boundary candidates (no implementation)

The spec's Go boundary is about **where the JS runtime's guarantee ends**.
Two durable invariants make a Go re-implementation plausible; the remaining
gaps are enumerated honestly:

1. **The committed-response bytes.** `FinancialOperation.responseBody` is
   stored as serialized wire text keyed by `(userId, endpoint, key)` with a
   canonical-request fingerprint. A Go replay authority could serve the
   committed bytes with no JS involvement — the table is the whole contract.
   The middleware's CAS semantics (`IN_PROGRESS` → `COMMITTED`, unique
   `(userId, endpoint, key)`, fingerprint compare) are specified in
   `r42-shared-idempotency-authority.md` and portable.
2. **Double-entry settlement postings.** Ledger postings (`ledger:*` keys,
   `LedgerTransaction`/`JournalEntry`) are idempotent inside the economic
   transaction already; Go could own matching + posting for hot paths
   (order book matching is the natural first candidate) while JS keeps
   orchestration.

Gaps that must be closed before any migration:

* **Prisma transaction semantics** — the in-tx claim CAS relies on the
  Postgres transaction containing both the economics and the claim write.
  Any Go path must produce the same single-transaction scope or the wired
  contract is void.
* **Byte-fidelity serialization** — `JSON.stringify` key order and Prisma
  `Decimal` → string coercion are load-bearing. A Go serializer must be
  proven byte-identical against the stored `responseBody` before serving.
* **Provider-boundary sequences** (deposits, cross-border rails) need a
  resumable workflow record before any language move — see the excluded
  list above.
